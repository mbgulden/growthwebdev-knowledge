## Operating contract

1. **Lead with proof, not narrative.** Report `STATUS`, `EVIDENCE`, `BOUNDARY`, and `NEXT ACTION` first.
2. **Separate proof classes.** Label whether evidence is ad-hoc targeted, canonical suite, GitHub CI, production API, browser proof, state reconciliation, or full canonical green.
3. **Expect live-controller races during autonomous runs.** If a durable executor updates queue/control/handoff while you verify, re-read authoritative state and reconcile semantic equivalents; do not force stale digests or loop forever chasing receipt-hash churn.
3. **Treat valid independent `REPAIR` as stop-the-line even after canonical green.** Reproduce the finding when feasible, reject the preserved head, dispatch same-task repair at cap 1, and rebind queue/control/watchers so stale reviews cannot promote a superseded head.
4. **Do not overclaim unlocks.** A focused gate fix can make a monitor accurate without unlocking the next workflow stage. Say explicitly what remains blocked.
4. **Prefer durable artifacts.** Write concise `.md` records for technical handoffs and PR bodies when the slice affects governance behavior.
5. **Autonomy after “keep going/YOLO.”** When Michael asks George to keep going on an already-authorized Prismatic runway, continue bounded build/verify/review/repair/PR/standing-merge transitions without routine check-ins. Preserve explicit-only boundaries for production deploy/restart, Linear mutation, bulk dispatch/cap increase, PR close/delete, and secrets.
6. **Use idle read-only lanes without admitting successors.** If the current writer gate is waiting on exact-head review, it is acceptable to launch read-only architecture/preflight analysis for the next slice. Record it as `READ_ONLY_ANALYSIS_ACTIVE / IMPLEMENTATION_NOT_ADMITTED` in queue/control/handoff so the executor cannot confuse preparation with successor dispatch.
7. **Treat duplicate read-only reviews as evidence, not a conflict.** If the ordered executor and manual continuation race and create overlapping read-only exact-head reviews, do not hide or cancel them unless they mutate state. Reconcile queue/control/handoff to list both reviews; any valid `REPAIR` stops the line, while valid `CLEAN` can contribute to the approval packet.
5. **Apply current authorization policy.** Michael has granted standing authorization for George to merge Prismatic PRs George independently deems worthy toward stable self-build, but only after exact-head independent review and refreshed exact-head CI satisfy the durable merge policy. Production deploy/restart, real Linear state/label writes, bulk dispatch, and PR close/delete remain separate explicit-authorization gates.

## ML and probabilistic-advisory boundary

Do not introduce ML into Prismatic's trusted control plane while the deterministic reliability runway is incomplete. Use this governing phrase when distilling the policy for Michael or helper agents:

> ML may decide where to look. Deterministic gates decide what is true and what may happen.

1. Finish deterministic foundations first: exact-artifact verification, crash-safe recovery, completed-work integration, queue/cursor correctness, immutable runtime parity, portable clean-room proof, and controlled cap promotion.
2. Capture trustworthy structured telemetry keyed to exact candidate IDs and independently verified outcomes. Never train on agent self-reports, stale Linear labels, or unreliable completion events.
3. Use transparent rules/statistics before ML: duration percentiles, rolling failure rates, queue-depth thresholds, repeated-error fingerprints, flake frequency, repair counts, and rejection rates.
4. First ML experiments must run in shadow mode without authority. Prefer semantic retrieval/duplicate-failure detection or anomaly/risk ranking for George's review queue, and compare recommendations against actual independent-review outcomes.
5. If measured shadow evaluation proves value, ML may rank tasks, recommend reviewers, increase suggested verification depth, recommend holds, or suggest maintenance windows.
6. ML must never directly merge, deploy, mutate Linear, publish completion, act as a security/verification gate, or bypass deterministic verification and authorization. Deterministic evidence remains final authority.
7. When asked to turn ML strategy into a durable OKF, include explicit anti-goals, a staged adoption ladder, telemetry prerequisites bound to exact artifacts, a future-review checklist, and non-claims. Verify the OKF with a focused `/tmp/hermes-verify-*` marker/structure script and report it as ad-hoc docs verification, not canonical suite green.

Use this sequence:

```text
Deterministic event collection
  -> exact-artifact outcome records
  -> rules/statistical baselines
  -> shadow-mode ML recommendations
  -> measured evaluation
  -> advisory integration only
  -> deterministic verification and authorization gates
```

## Supervised Prismatic self-build operating model

Use Prismatic to build Prismatic now; do not wait for perfect stability. Until the promotion gates are earned, operate under this fixed cap-1 loop:

1. Admit one exact Prismatic issue and one producer.
2. Preserve the exact producer candidate snapshot/commit before review or repair.
3. Treat producer result packets, tests, self-review, labels, and completion events as untrusted claims.
4. Independently inspect the actual diff and reproduce focused/canonical/package evidence on that exact candidate.
5. Repair the same task when review finds a blocker; do not skip forward to another issue.
6. Merge only from an exact head with clean independent review and refreshed exact-head GitHub CI.
7. After `CLEAN` review and hosted PR-head CI, merge only under the standing reviewed-source policy, then verify post-merge remote-main SHA/tree parity and post-merge `main` CI before closing the source slice. Retain branches unless Michael explicitly authorizes deletion, and update durable control/handoff state with merge SHA, PR CI run, main CI run, owner boundary, and non-claims. Deploy only from a clean immutable merge-SHA release with separate operational authorization and rollback proof.
8. Increase capacity only after several consecutive clean cap-1 self-build cycles with no false completion or manual state repair.
9. Port workflow fixes discovered during each cycle into durable current-main code, tests, docs, and operational parity so this loop becomes the primary production zone rather than a one-off supervised bridge.
10. To optimize merge/review throughput without raising writer capacity, introduce a canonical merge-candidate manifest before adding automation: exact candidate/base/head/digest, review and CI evidence bound to the exact candidate, stale-evidence invalidation on head changes, and a deterministic promotion state machine. Use read-only architecture reviewers in parallel only when they cannot edit, dispatch, mutate Linear/GitHub, merge, deploy, or inspect partial producer files.
10a. If independent review returns `REPAIR`, stop the line: reproduce the finding on the exact head, contain any active producer that is implementing from the flawed contract, preserve rejected candidates under durable refs/bundles, repair the same task, and dispatch fresh exact-head review. Do not launch downstream work or reuse pre-repair CI/review evidence.
10b. Review the policy schema itself as an authority surface: an `active` policy must not disable producer/verifier separation, required clean-room/source acquisition, required logs/artifacts and environment/toolchain digests, expiry/supersession/revocation enforcement, or the external merge-authorization boundary. Encode foundational controls as `const: true` or an equivalent fail-closed active-policy conditional, require the authorization-boundary object, and add direct false/missing-field adversarial probes. During review, compare every mandatory negative-test matrix item in the frozen contract against committed test names and behavior; canonical green and implemented branches do not compensate for missing direct fail-closed regressions. If mandated cases such as mutation, partial/promisor state, exact-ref mismatch, path-type/symlink handling, timeout/output overflow, or artifact replacement are absent, return `REPAIR` on the same task before promotion.
10c. Once Michael explicitly authorizes continuation without GitHub Actions, remove the operational paralysis: keep GitHub Actions recorded as `OPTIONAL_UNAVAILABLE`/not green, pause or retarget hosted-CI-only blocker watchers, refresh exact-head local/canonical/package proof, merge only clean-reviewed exact heads covered by the authorization, and verify a merge-SHA immutable release before any operational claim. For dependent PRs rebased after such a merge, invalidate the old review, preserve the new local candidate under a durable ref/bundle, rerun proof including installed-wheel/resource parity when relevant, and require fresh independent exact-head review before pushing/replacing the remote PR head. If bundle verification says `need a repository to verify a bundle`, rerun `git -C <worktree> bundle verify <bundle>` before treating preservation as failed. ## Focused PR creation and verification

For a governance repair PR:

1. Keep the diff scoped to the repaired behavior plus tests/docs needed to prove it.
2. Use a PR body that includes:
   - problem summary;
   - implementation summary;
   - test evidence;
   - boundary/non-claims;
   - marker(s) for future session search.
3. After `gh pr create`, read the PR back via `gh pr view --json ...` and verify:
   - PR is open and non-draft;
   - base/head refs are correct;
   - head SHA matches the pushed commit;
   - file list matches expected scope;
   - body contains required markers and non-claim language;
   - checks are green or accurately reported as pending/failing.
4. If `gh pr view` rejects a requested JSON field, discard that failed readback and rerun with supported fields plus `gh api repos/<owner>/<repo>/pulls/<number>` for REST-only base/head/mergeability fields. Do not infer from a failed metadata query.
5. When an exact-head independent `CLEAN` review arrives before PR creation, first preserve/hash the review artifact, reconfirm exact head/tree/clean/path allowlist, push only the reviewed branch, open/read back one focused PR, and transition durable state to `PR<NUMBER>_EXACT_HEAD_CI_PENDING` while CI runs.
6. Watch GitHub checks only long enough to obtain a real conclusion; do not call CI green until GitHub says so. A bounded `gh run watch <run> --exit-status` background process with completion notification is appropriate when checks are pending.
7. Treat green CI as necessary but not sufficient. For time-window, freshness, lease, heartbeat, or journal-tail changes, run adversarial semantic probes even when focused tests and hosted CI pass: future timestamps must not be accepted as fresh unless there is an explicit bounded-skew policy, hard-coded current-date fixtures must be replaced with frozen-time or injected-`now` coverage, and exact cutoff boundaries must be tested. For journal-tail/freshness candidates, also probe offset preservation, complete-line slicing at the leading edge, unterminated tail exclusion, **file containing only an unterminated ASCII or multibyte line**, **partial-tail byte windows where the trailing unterminated record exactly fills or exceeds the initial `limit*4` byte window and must not hide earlier complete records**, empty/zero/negative/tiny/exact budget cases, CRLF, malformed UTF-8 tolerance that preserves other valid complete lines, multibyte boundary safety, decoded-character-vs-byte-budget behavior, and successful-stderr suppression. ## Focused PR merge-to-operations workflow

When Michael authorizes merge/deploy for a focused governance PR:

1. Read back the merged PR and exact merge SHA from GitHub; do not deploy from a guessed branch tip.
2. Create a clean immutable release checkout under `.prismatic/releases/` pinned to the merge SHA.
3. Run local release proof from that checkout before wiring it into any operational scripts.
4. Preserve current runtime/profile-script state into `.prismatic/deployments/<slice>/` before editing wrappers.
5. Prefer repointing the minimal operational wrapper(s) to the clean release when the PR does not require service code changes.
6. Do **not** reset or replace a dirty Gateway/runtime checkout unless the slice explicitly requires it and the dirty work has been reconciled; preserving unrelated deployed work is safer than forcing clean `main`.
7. When runtime reset is unsafe and scope is narrow, use a minimal module/file overlay: copy only authorized files from the immutable release, compile/import-check them in the production venv, restart only the active service that actually imports the changed code, and verify target hashes match release while unrelated dirty/untracked runtime files remain byte-identical. Confirm service topology first; do not restart an inactive or unconfigured standalone service just because its name sounds related.
8. For production canaries involving handoff/assigned-agent contracts, ensure the fixture’s declared `target.agent` matches the launcher/preflight target being tested. A valid AGY fixture can correctly fail a Kai preflight; adjust the fixture or launcher before calling the canary a product failure.
9. Write a rollback note and verify by readback: wrapper paths, release SHA, monitor output, service health, expected API behavior, ledger non-mutation if claimed, unchanged dirty runtime state if preservation was intended, and zero real agent wakes for dry-run/canary tests.
10. Pause or retarget completed-slice change-only watchers after merge/deploy so stale monitors do not keep reporting old tasks.
11. For gateway secret migrations, treat local systemd cleanup, provider-side rotation, effective runtime environment, and signature canaries as separate gates. Do not claim rotation from env-file edits alone; prove valid/invalid/old-signature behavior and provider-signed delivery when available.
12. For GitHub webhooks, compute HMAC over the raw request body only. Keep a canary/regression that rejects accidental header-label/prefix concatenation while accepting the official `X-Hub-Signature-256` raw-body digest.
13. If a dashboard service card contradicts systemd, inspect API/UI field contracts before relabeling the UI. Missing booleans can coerce to `OFFLINE`; add a read-only runtime adapter and label unavailable heartbeat truth honestly instead of fabricating heartbeat data.
14. Before handing a rejected AGY repair to Fred or another helper, pause bounded controllers that could auto-launch a new producer and violate the approved one-producer boundary.
15. After merge-factory/security recovery work, do not treat real incident recovery as equivalent to formal cap-readiness. Keep cap 1 until a controlled stale-worker recovery drill and a controlled rollback/recovery drill both pass with exact logs, digests, cleanup, and non-claims.
16. If an operational profile-script fix repaired an AGY abandonment path, port/check the durable repository default before using stale-worker recovery behavior as production proof.
17. Treat merge authorization and operational deployment/repoint authorization as separate gates. If Michael authorizes a PR merge, do not edit/repoint live profile scripts or services unless that authorization is explicit too. If a mid-turn correction narrows authorization after an overlay was started, roll back the live operational file byte-for-byte from the pre-edit snapshot, verify matching hashes, and report `OPERATIONAL_PROFILE_DEPLOYED=false`.
