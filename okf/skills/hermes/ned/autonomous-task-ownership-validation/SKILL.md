# Autonomous Task Ownership Validation

**Core principle: ownership mismatch is a routing bug, not your problem to paper over.**

When a cron, orchestrator, or wakeup prompt hands you N Linear issue IDs and says "execute them," the FIRST step is ownership validation — not execution. Running `finalize_task.sh` on a misrouted issue is worse than not running it at all: it commits empty noise, marks the issue "In Review," and writes a false evidence comment to Linear.

## The Validation Sequence (run on EVERY cron-fed task list)

1. **Read the issue contents, not just the ID.** The ID is a pointer, not a permission. Fetch title, description, priority, labels, and current state for each.
2. **Cross-check label vs. content.** If every issue carries an `agent:<your-name>` label but the content is clearly for other agents (Human Design bot = Sage, tax/compliance = Sam, social media = content team), the label is stale or the routing sweep misfired.
3. **Cross-check description vs. your lane.** Does the work involve your actual responsibilities? (For Ned: GPU nodes, disk, GitHub hygiene, Cloudflare, swarm agents. For Sam: tax filing, compliance, entity profiles. For Sage: HD readings, transits.) If zero overlap, refuse to execute.
4. **Check state.** Issues already in "Done," "Cancelled," or "In Review" need different handling than "Backlog" or "Todo."

## Decision Tree

```
N Linear IDs arrive
  │
  ├─ All match my lane → execute, finalize, report
  │
  ├─ Mixed (some match, some don't) → execute the matching ones,
  │   flag the mismatches with ownership suggestion
  │
  └─ None match my lane → DO NOT execute any. Report:
       - routing error (label sweep misfire)
       - suggested correct owner per issue
       - any genuine infra findings uncovered during validation
```

## Stale-Backlog Sweep: Repeat-Tick Handling

The "Case Study" below described a single encounter. In practice, the misrouted 10-item batch can recur every cron tick (15 min) for hours until Michael fixes the upstream `scan_tasks.py` filter or re-assigns labels. **The second tick is NOT a new refusal — it's the same event with a different timestamp.** Detect and respond differently:

0. **Run `scripts/probe_recurrence.sh` FIRST.** It fetches the anchor's most recent Ned-triage comment timestamp, computes age in minutes, applies the suppression-decision table below, and prints `SUPPRESS` vs `POST_FRESH_TRIAGE` with a one-line reason. Don't re-fetch the issue list by hand — the probe is one GraphQL roundtrip and removes the temptation to "just post one more comment because I'm already here." Default anchor = `GRO-570` (June 2026 photo-sweep anchor).

   **⚠️ Anchor-shift pitfall (r153):** the probe's default anchor (GRO-570) only applies when GRO-570 is in the current scanner feed. When the scanner rotates to a fresh misroute batch, the **effective anchor shifts to whichever batch-member carries the most recent Ned-triage comment**. Always sanity-check by manually querying `comments(last: 10)` on the most-touched batch member and using that issue's `MAX(createdAt)` as the recurrence baseline. The probe's default-anchor age is informational only. See `references/ned-r153-batch-anchor-shift-20260629.md` for the full reasoning.

   **Note (NEW 2026-06-27 r52):** GRO-570 may move out of Backlog into In Review at some point during the rN+ chain (it did at r52) — if the probe's filter excludes In Review, the anchor disappears from the team-level query and you need to either broaden the filter or do a separate In Review lookup. Mutations like `commentCreate` still work on In Review issues — only Canceled/Duplicate reject them.

   **Invocation:** the file is named `.sh` but has `#!/usr/bin/env python3` shebang — invoke with `python3 <path-to>/probe_recurrence.sh`, NOT `bash`. Calling `bash probe_recurrence.sh` produces a wall of `command not found` / `command substitution` errors (the file is parsed as bash, hits the docstring on line 5, and chokes). Same rule for `check_ned_queue.sh`. `verify_gpu_node.sh` is the inverse — it's real bash with a Python-style filename, so `bash verify_gpu_node.sh` is correct and `python3 verify_gpu_node.sh` fails on the awk pipeline. The filename lies to the eye; the shebang is the truth. If you're unsure, `head -1 <script>` and use the matching interpreter.

1. **Detect recurrence.** Pull each issue's `updatedAt` and the timestamp of the last triage comment on the canonical anchor. If the items in the scanner output are identical AND the last triage was within the last few hours, this is a repeat tick.
2. **Skip the new Linear comment** when the probe says SUPPRESS. Posting "same as last tick" comments pollutes the thread and trains reviewers to ignore the channel. The earlier comment already documented the routing bug.
3. **Still re-run infra probes.** Real infra findings (GPU down, disk climbing) can change between ticks — re-probe with `scripts/verify_gpu_node.sh` and report the **delta vs. last probe** (see "Infra probe discipline" below).
4. **Lead with the recurrence evidence.** Say "same 10 items as N min ago" with the deltas to make it impossible for Michael to miss.

**The full-filter statistic gets reused, not re-collected every tick.** If you already proved "0 actionable in the queue" in the last triage, restate the conclusion without re-running the broad query — but DO re-check if the In Progress set changed (someone may have finalized a real Ned task). The `scripts/check_ned_queue.sh` probe is the cheap way to do this.

**The recurrence gate runs UNCONDITIONALLY on every tick.** It is tempting to skip `probe_recurrence.sh` on what looks like a "fresh" encounter — e.g. Hermes VM restart, new cron install, profile re-init — because there's no in-session memory of a prior triage. But a previous cron invocation (hours or days ago) may already have triaged the anchor. The probe's value is not "did I triage this session" — it is "is there a recent triage on the anchor?" Treat it like the disk-probe and GPU-probe: mandatory infrastructure, not optional. **The probe is the only mechanism that prevents a 15-min cadence from producing 96 Linear comments per day.**

### Item-list drift: when the same sweep returns with items added/removed

Recurring sweeps aren't always identical. Between ticks the scanner can pick up newly-touched Backlog items and drop items that were just transitioned to Todo/In Progress (or vice versa). **Decision rule** for whether to post a new triage comment:

| Last triage age | Items identical to last triage? | Action |
|---|---|---|
| <2h ago | yes | Suppress comment, brief cron reply only |
| <2h ago | no (≥1 add/remove) | **Post fresh triage** with what-changed-since-last-triage delta |
| 2h–24h ago | yes | Suppress (recurring sweep, dequeue already documented) |
| 2h–24h ago | no | **Post fresh triage** with drift delta |
| >24h ago | either | **Post fresh triage** (anchor stale; prior triage no longer represents the current state) |

**r59 mechanical-SUPPRESS rule (June 2026):** when last triage age is in the 2h–24h window AND items identical, the decision collapses to **SUPPRESS** regardless of whether the prior comment was a full triage or a recurrence statement — the thread is already current, the routing bug is already documented, and a new comment only adds noise. **r153 confirmation:** when last triage age is in the literal <2h window AND items identical, r59's rule still applies — SUPPRESS. The "literal r59 case" (items identical + last triage <2h) was confirmed on 2026-06-29 r1 against the GRO-485 batch anchor.

**Carry-over escalations are real infra findings, not routing noise.** During sustained-SUPPRESS on a recurring misroute batch, the thread carries genuine escalations (GPU ~57h+ down, GRO-565 tax deadline ~13 days lapsed). Audit `okf/audits/ned-scan-triage-2026-06-28-r1.md` written; index row added.

**Refinement:** the r59 mechanical-SUPPRESS rule continues to apply *within* a calendar day for slot rotations and identical-feeds — but it does NOT carry across a calendar boundary unless the next-day script feed happens to be identical to the prior-day's last audit. In practice this almost never happens (the scanner rotates daily as items move between Backlog/Todo), so the safe default is: **new day → new r1 → fresh triage.** The "is this a new day?" check is `date -u` vs the prior audit's `YYYY-MM-DD` prefix; if they differ, start r1.

**On the 32-minute follow-up tick at 2026-06-26 02:07Z** is the canonical **suppression** example: items identical, prior triage 32 min old, no drift. Probe returned `SUPPRESS` and the cron reply was a 6-line recurrence statement + infra-delta table. No Linear comment, no `finalize_task.sh`.

**First-encounter variant — when this session has no in-session memory of a prior triage.** 2026-06-26 ~02:26Z cron tick ran with the same 10-item misrouted Backlog batch (GRO-608/575/572/571/570/568/567/565/564/563) but the session had no prior in-session triage on file. The agent correctly refused execution, reported the routing bug per the 3-component template, surfaced the GPU-down infra finding, did NOT run `finalize_task.sh`, and did NOT post a Linear comment. **However**, it skipped the recurrence probe — assuming "first sight" meant "no prior triage exists." Running the probe would have returned `SUPPRESS` and produced the 6-line recurrence format instead of a longer ad-hoc refusal. **Lesson: the probe discriminates "I haven't seen this" from "no one has recently commented" — they are different questions, and the probe answers the second one, which is what matters.**

### The "1 In Progress, no human-review label" edge case

The classic "0 actionable" conclusion assumes actionable items are in Todo or In Progress without `agent:needs-human-review`. **Watch for the 1-item In Progress carve-out**: an issue can be In Progress, carry only `agent:<you>`, and still be unactionable for a cron job if it requires hands-on work (physical hardware, in-person meetings, real-world payments). On 2026-06-26 the queue had exactly one such item — **GRO-703** "Harvest Mellanox NICs + HGST SSDs from 10x DL380 chassis" — which is Ned's lane and labeled `agent:ned`, but physically unactionable from SSH. Surface it in the triage with explicit reasoning ("looks actionable but requires physical chassis access — not autonomous-executable") so Michael doesn't later wonder why it wasn't picked up.

## Remote-Resource Acceptance Checks: Do Not Duplicate Already-Completed External Work

Some Ned-lane tasks ask to create or configure a remote resource (a private GitHub repository, Cloudflare object, deployment setting, etc.) while Linear has no prior evidence comment. That absence is **not** proof the resource is absent.

Before mutating the remote system:

1. Query the exact requested resource using the authoritative API/CLI and read back the acceptance fields (for example GitHub owner/name, visibility, default branch, permissions, and canonical URL).
2. If it already satisfies the task's requested state, **do not recreate, rename, or alter it merely to make the task look newly executed**. Record the readback timestamp, immutable identifier/head where applicable, and the exact creation/configuration command that would have been used only if absent.
3. Finalize it honestly as a verification/acceptance pass, with an explicit non-claim that this cron execution did not create or alter the existing resource. Store the evidence in `/tmp/issue-batches/<ISSUE>_RESULT.md` before finalization, then rewrite it after finalization with the authoritative Linear state/comment readback.
4. If the resource exists but misses an acceptance field, make only the permitted, narrowly-scoped correction; do not use a different permanent name or broaden the task.

This prevents duplicate remote resources and preserves a truthful audit trail when an upstream task was performed before its Linear child was finalized.

### Remote-readback finalization refinement

For an already-compliant remote repository, preserve the acceptance readback in a focused target-repo documentation PR rather than mutating the remote setting merely to create activity.

### Conflicting issue-local execution contracts

Linear descriptions can carry a generic contract that conflicts with Ned's governed skeleton (for example `feature/...` instead of `ned/...`, `[AGENT]` commit prefix instead of `[Ned]`, or `Done` instead of the review-stage state required by the finalizer). Treat the platform/profile governance as authoritative for branch naming, lock ownership, commit format, and finalization state. Preserve the task's *acceptance evidence*, but do not follow its generic workflow instructions when they would violate an enforced lane convention. In the evidence packet, explicitly record the actual branch/PR/state so the deviation is auditable rather than silent. Invoke `finalize_task.sh` with `PRISMATIC_REPO_ROOT` set to that actual target checkout and `FINALIZE_LOCK_FILES` set to the exact acquired lock. Its printed transition is not authoritative: re-query the issue and evidence comments immediately, correct any `In Progress` drift to the target team's `In Review` state through the variables API, then read back again. Do not infer newest-comment order from `comments(last: 1)`; fetch several and assert the expected comment ID is present. See `references/remote-repository-readback-finalization.md` for the full verification and src-layout pytest recipe.

## Parent-epic and child-gate coordination

### Dependency-gated child dispatches

A scanner can dispatch a *child* that itself depends on unfinished siblings (for example, an isolated lifecycle-proof task that requires an adapter/discovery child and a control-plane bridge). Treat the dependency list and the issue's existing dependency-gate comment as authoritative acceptance gates:

1. Query the assigned child, every named dependency, and its parent; record their exact persisted workflow states and inspect recent comments before acquiring a code lock.
2. If a required integration surface remains `Todo`/unaccepted, do not manufacture a substitute proof from older reference code already in the checkout. Existing lifecycle helpers or historical branches are not evidence that the current child contract is satisfied.
3. Do **not** run `finalize_task.sh`, acquire a lane lock, create a branch, or run an unrelated test suite. Those actions either create false delivery signals or consume another agent's working surface without an executable acceptance target.
4. Search OKF, session history, and the relevant environment-key presence before calling this blocked. Then write/refresh `/tmp/issue-batches/<ISSUE>_RESULT.md` with dependency-state matrix, explicit non-claims, and resume condition.
5. When the same dependency gate was already commented on recently and state has not changed, suppress a duplicate Linear comment. The local result packet and concise cron report are the correct fresh evidence; Linear comment churn is not progress.
6. On every repeat dispatch, re-query the child, every named dependency, and the parent in one variables-based GraphQL request before refreshing the packet. Assert each expected workflow state from the response; do not treat a prior packet or prior cron report as current evidence. Include the exact check time, explicit non-claims (no lock/finalizer/deploy/test), and resume criteria in `/tmp/issue-batches/<ISSUE>_RESULT.md`, then validate required markers and scan the packet for credential-shaped strings. If another worker has already touched that packet, read it before replacing it so fresh evidence is merged rather than silently discarded.

- **`finalize_task.sh` `--blocker` flag ignored or misbehavior:** The `finalize_task.sh` script may not correctly interpret the `--blocker` flag or may incorrectly transition Linear issue states (e.g., to "In Review") and unlock files even when a genuine blocker (like a lock held by another agent) exists. **Always verify Linear state and lock status independently after running `finalize_task.sh`**. If the script's output is not authoritative, manually correct Linear state and comments.
- **Critical `HERMES_LINEAR_API_KEY` missing:** Tasks requiring Linear updates (state transitions, comments) will be blocked if `HERMES_LINEAR_API_KEY` is not available in the environment. This is a critical credential and its absence warrants immediate escalation.

### Pitfall: `finalize_task.sh` with Dependency Blocks

When a task is blocked by dependencies, `finalize_task.sh` may attempt to transition the Linear issue to \"In Review\" (or another inappropriate state) and post a misleading comment. **DO NOT run `finalize_task.sh` if the task is genuinely blocked by dependencies and cannot be worked on.** Instead:

1.  **Release any acquired locks manually:** `node /home/ubuntu/.antigravity/swarm.js unlock <repo> <agent>`.
2.  **Add a comment to Linear directly** using the `commentCreate` mutation via `curl` (or `requests` in `execute_code`), explicitly stating the dependency block, the blocking issue IDs, and their current states. Ensure correct API key handling and mutation name (`commentCreate`).
3.  **Do NOT change the Linear issue state** if it's already in an appropriate state (e.g., \"Todo\"). If it's not, manually transition it to \"Todo\".
4.  **Report the blockage concisely** in your final cron output, including the issue link and blocking dependencies.

A cron can assign a parent epic whose acceptance criteria are explicitly the union of child gates. Treat the parent as a coordination/verification task, not permission to finalize unfinished children.

1. Query every named child issue and the candidate branch/PR before acquiring a broad implementation lock or running the finalizer.
2. If a required child is `Todo` or `In Progress`, or required evidence (for example lint/format/compile or secret scan) is absent or red, **do not run `finalize_task.sh`** on the parent. It would falsely move the parent to `In Review`.
3. Record an authoritative parent result packet in `/tmp/issue-batches/<PARENT>_RESULT.md`: target/branch/head, child-state matrix, exact blocker, prior proof scope, and explicit non-claims.
4. Post one concise Linear coordination comment only when there is no current equivalent evidence; keep the parent in `Todo`, verify that state/comment read back, and release any acquired lock manually.
5. Do not “fix” an active child owned by the same queue merely to complete the parent. Resume parent proof only after the final candidate commit contains green evidence for every required child gate.

This applies even where earlier standalone checks passed: a wheel/import/test proof does not substitute for missing lint, format, compile, secret-scan, or final-manifest acceptance gates.

### Conflicting parent-candidate refinement

When the parent already has a conflicting consolidation PR, preserve it as evidence and create a fresh `ned/<PARENT>` consolidation branch/PR instead of force-pushing or reusing that stale path. Rebase onto current `main`; for redundant or formatting-only conflicts retain the current-main compatibility baseline, then verify every required child gate remains present. Run the complete isolated acceptance proof and wait for the new PR's CI before presenting the parent as review-ready. Finalizer output remains non-authoritative: re-query Linear state/comment and the actual acquired lock after it runs, correct any `In Progress` drift, then rewrite the parent RESULT packet. See `references/parent-consolidation-clean-pr-proof.md`.

## Finalize / lane-rejection recovery

When a task's requested path is outside Ned's enforced push lane, `finalize_task.sh` may still transition Linear before the push fails. A local commit is then only a handoff candidate, not completed work. Before finalizing, pass the actual acquired path through `FINALIZE_LOCK_FILES`; afterward, read back Linear state/comments and inspect that exact lock path. If push is rejected, preserve a checksumed `/tmp/issue-batches/<ISSUE>-handoff/` patch, explicitly release the actual lock, restore Linear to `Todo` with a corrective evidence comment, and re-query the persisted state. Never bypass the safe-push lane guard merely to make the issue look finished. Use the fresh artifact-verification recipe in `references/finalize-lane-rejection-recovery.md`.

## The "Theater" Failure Mode (NEVER DO THIS)

Bad: "Finalize script says commit-empty and mark In Review, so let me run it for every ID even if I did no work."

Why it's bad:
- Linear comment thread gets a fake evidence post
- Issue moves from Backlog to In Review, polluting the workflow
- Empty commits pollute git history
- Michael sees "10 issues moved to In Review" and assumes progress was made
- The actual owners never get pinged because the issue is no longer in Backlog

Good: "All 10 issues are misrouted. Running finalize would lie. I'll report the routing bug and the real infra findings instead."

## Infra probe discipline: always show delta vs. last probe, not just current values

Pitfall hit on 2026-06-26 02:07Z: reporting disk at "82%" without comparing to the prior probe's 81% taken 32 min earlier nearly lost the rate-of-change signal (+1%/h vs the established +1%/8h baseline).

Rule for Component 3 (the infra-finding section of any triage or repeat-tick reply):

- **Always table the delta.** Format: `| Probe | HH:MMZ | HH:MMZ | Delta |` with one row per probe. Two prior readings are better than one — establishes the trend.
- **Flag rate anomalies explicitly.** "Disk +1%/h vs prior +1%/8h baseline" is a different and more urgent signal than "disk at 82%". The absolute value matters less than the rate.
- **State unchanged = state confirmed.** A "100% packet loss / 100% packet loss" row is not filler — it confirms the failure is persistent across the re-probe window. Don't shorten the table to save space; the reader needs the confirmation.
- **Run `scripts/verify_gpu_node.sh` on every cron tick**, even when suppressing the Linear comment per the recurrence table. The recurrence decision is about Linear-thread spam, not infra-monitoring discipline.
- **No "delta = 0" rows.** If a probe didn't change, write "unchanged" — saves space and tells the reader the re-probe ran.

### Suppression-with-Infra-Escalation: when SUPPRESS still requires a longer reply

A SUPPRESS verdict governs the Linear channel — it does NOT suppress the cron reply. The cron reply is itself the delivery channel for infra findings. If a SUPPRESS tick produces a clean infra-delta table with no findings, then a 6-line reply is right. If the delta table shows a rate anomaly crossing the tiers below, escalate in the same reply — don't suppress the entire tick.

**Escalation tiers** (the cron reply itself must escalate these even when the Linear channel is suppressed):

| Severity | Trigger | Reply shape |
|---|---|---|
| Warn | Disk ≥ 85% OR GPU unreachable 1–12h | Brief callout in reply, no separate escalation |
| Critical | Disk ≥ 90% OR GPU unreachable 12–72h OR rate anomaly ≥ 10× baseline | Full infra-delta table + cleanup-target list, even on SUPPRESS tick |
| Catastrophic | Disk ≥ 95% OR GPU unreachable > 72h OR imminent failure mode | Reply includes explicit "Michael action required" with specific intervention steps |

**Rule of thumb:** suppression keeps the Linear thread clean; it does NOT suppress the cron reply. If a SUPPRESS tick produces a clean infra-delta table with no findings, then a 6-line reply is right. If the delta table shows a rate anomaly crossing the tiers above, escalate in the same reply — don't suppress the entire tick.

- **Already-finalized redispatch refreshes:** when a cron scanner re-dispatches an issue whose remote branch is present, Linear is already `In Review`, PR/finalization evidence exists, and the shared checkout is dirty/on another task, treat it as a verification-refresh pass — not a rebuild. **Do not over-apply this shortcut:** `In Review` plus a generic finalize comment is not proof of completion when the local RESULT is missing, no PR exists, or the last comment lacks concrete verification. In that case, use a clean temp worktree from the remote task branch, inspect the implementation for runtime import/contract gaps, run focused tests plus a fresh `/tmp/hermes-verify-*` verifier, add any small missing glue/docs/tests, push, open the PR against the source/master-plan branch when appropriate, rerun `finalize_task.sh`, then post a Linear evidence-refresh comment with the real verifier output.
