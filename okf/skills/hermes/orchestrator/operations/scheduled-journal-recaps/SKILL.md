# Scheduled Journal Recaps

## When to use
Use this skill when a cron/scheduled agent is asked to turn an inbox, snapshot log, notes file, commitment digest, morning briefing source, or daily activity stream into a durable journal/recap file or user-facing briefing. This includes Becca/next-step style journals, local-only cron jobs, and recap jobs where the final delivery may be `[SILENT]` if there is nothing useful to report.

## Archive-gap self-check (2026-08-26, Becca)

Before synthesizing, check that the **previous day's recap file exists** (for a 08-26 run: `journals/2026/08/25.md`). A missing prior recap is a signal about the **recap pipeline**, not the wire — keep the two strictly separate in the memo. When found:

1. **Isolate the break**: confirm the prior day's INBOX file has full hourly cadence (24 snapshots = collector was healthy; the gap is in the recap run, not the collector).
2. **Record with a pattern trigger**: note the gap in the current day's Work completed + Follow-ups as **one miss = blip (note it, no alarm); two consecutive misses = investigate the recap cron itself** (check its run history). Name the gap plainly in the memo.
3. **Do not backfill** the missing day retroactively — the journal is a daily record; the gap note is the record.

Observed 2026-08-26: no `08-25.md` existed even though the 08-25 inbox was a full, healthy 24-snapshot day. The 08-26 recap caught it, isolated the break to the recap run, and logged the two-miss trigger in Follow-ups.

## Recap-side health signals to surface

The W30 weekly rollup (2026-07-26) surfaced several Hermes-side issues that recaps should keep surfacing until PE ownership lands. A good recap does not just synthesize the day; it also flags the operational health of the journal pipeline itself.

- **`prismatic-journal-snapshot` CLI broken.** The `ModuleNotFoundError: prismatic` error from 2026-07-21 was patched by running with `PYTHONPATH=/home/ubuntu/work/prismatic-engine`. Until the PE cron stub ([GRO-4255](https://prismatic.growthwebdev.com/tab/tasks?issue=GRO-4255)) lands, the cron depends on this environment variable.
- **Git collector stderr.** Daily journals inherit `fatal: not a git repository` from the git collector running outside the journal repo. Suppress in the recap; keep it out of the operator-visible summary unless the user explicitly asks for raw stderr.
- **gdrive MCP path expansion.** `Cannot find module '/$PRISMATIC_HOME/work/local-gdrive-mcp/server.js'` — literal `$PRISMATIC_HOME` not expanded. Until repaired, do not surface gdrive MCP errors as journal-side blockers.
- **Cron handler collisions.** The `fred`-profile gateway PID collision (07-26: PIDs 1635792 → 1686702 → 1707185) showed that long-running handler instances can collide. Until stabilized, recap-side health includes a per-process check.
- **AGY / Autobot misclassification.** `AGY Auto-Re-Arm Watchdog` errors climbing week-over-week; `Autobot Factory Health Aggregator` misclassifies success as failure. Surface these in the recap's Blockers section without diagnosing them — diagnosis belongs to the watchdog owners, not the recap.

## Core principles
- **Read the source of truth first.** Determine today's date in the requested timezone, then read the exact inbox file and the template before writing. For commitment digests with Linear identifiers, treat live Linear state as canonical over local journal/commitment JSON before surfacing a blocker.
- **Synthesize, do not dump.** Convert raw snapshots into a cohesive memory entry covering memo, work completed, decisions, sources/links, blockers, and follow-ups.
- **Respect the recipient lens.** If the journal belongs to a Human Design profile, frame insights lightly and practically; do not turn an operational recap into a horoscope.
- **Local-only means local-only.** Do not send messages or use external delivery tools when the job says the system will deliver the final response.
- **Verify the artifact.** Recap files are durable workspace artifacts; after writing, confirm the file exists, has required sections, includes key source references, and that `latest.md` or equivalent points to it.
- **Treat verification nudges as audit triggers, not as defensive questions.** If the user (or a verification guard) asks "is the recap verified?", the right move is to **run a fresh verifier** against the current artifact — not to cite prior verifications or return `[SILENT]`. The audit pattern from the W30 rollup is: re-read the inbox, write the recap, run `/tmp/hermes-verify-*.py` after the final edit, report the fresh evidence with the verifier path/exit code/cleanup. The audit log note explicitly says which layer was wrong when a failure happens (verifier anti-pattern vs recap content bug).

## Standard workflow
0. **GATE — Load this skill with `skill_view(name='scheduled-journal-recaps')` as the literal first tool call of the turn.** This is the first three-consecutive-drift precondition (2026-08-09) — it is not optional and not skippable when "I remember the recipe." As of the seventh consecutive drift event (2026-08-16), Step 0 is **enforced, not advisory**: any tool call made before `skill_view` in a Becca Journal Recap turn is a procedural violation. If you find yourself about to read the inbox, write the recap, or update the symlink and have not yet loaded this skill, **stop, load the skill, then continue**. If the recap path or inbox path is mentioned, the canonical `scripts/verify_becca_recap.py` is the right answer for verification — reaching for `execute_code` with inline verifier code (which produces no `/tmp/hermes-verify-*` file at all) or a fresh heredoc `tempfile` instead means you skipped the verification precondition and should stop, delete the custom verifier, copy the canonical script, and re-run. Reinventing the verifier is a tracked pitfall (see Pitfalls). **Verification-nudge re-fire protocol (2026-08-22):** if a nudge arrives AFTER a canonical verifier already ran green this turn, the answer is to re-run the same canonical copy (fresh invocation) — never a new custom matrix. A custom matrix that scores 40/40 can still be missing the canonical matrix's exact-string checks (see the 2026-08-22 drift entry in Pitfalls).
1. Resolve the date explicitly with a tool — **before the first inbox read**, not after. Usually `date -u +%F` unless the prompt names another timezone. The conversation-header date is advisory and can lag the real UTC date by a day (evening-started session rolls past UTC midnight before the 06:00Z cron fires). The system clock is the sole authority; on disagreement, the clock wins. (2026-08-19: header said 08-18, clock said 08-19 — the first inbox read hit the wrong day's file.)
2. Read the inbox for that date and the journal template. Use the canonical filesystem path (`/home/ubuntu/work/next-step-becca/journals/...`), not a `~/.hermes/profiles/.../home/work/...` — see HOME expansion trap below. **Before writing, check for missed days:** `ls journals/<YYYY>/<MM>/` and find the newest existing daily recap. If it is older than yesterday, audit every missed day's inbox (`grep -c "^## Snapshot"` vs count of "No new files" — equal means fully silent). All missed days silent → write only today's recap and disclose the gap in the memo (e.g. "no daily recaps were generated for Aug 17/18; both inboxes were audited and are fully silent, so nothing was lost"). Any missed day with activity → backfill that day's recap first, then write today's. (2026-08-19: 08-17/08-18 both 24/24 silent — disclosed, no backfill.)
3. If the inbox is empty or has no meaningful activity, either:
   - create a concise quiet-day recap if the job requires a file, or
   - return exactly `[SILENT]` only when no report/file is genuinely needed by the prompt.
4. Write the recap to the date-partitioned path requested by the job, preserving the template's major sections.
5. Update `latest.md` with a relative symlink when possible so the journal directory remains portable.
6. Run the canonical verifier: `cp scripts/verify_becca_recap.py /tmp/hermes-verify-becca-YYYY-MM-DD.py && python3 /tmp/hermes-verify-becca-YYYY-MM-DD.py YYYY-MM-DD`. Report exit code and the per-check status. **Leave the temp script on disk through the verification gate — do NOT `rm` it in this turn** (2026-08-22, per `prismatic-evidence-handling`'s 2026-08-13 lifecycle refinement, reproduced live: a green run + same-call `rm` re-triggered the "no fresh passing verification evidence" nudge the very next turn; recreate + leave-on-disk stopped it). Delete only after the gate has been quiet for a turn. Re-run on every verification nudge (state-per-turn — see Pitfalls).
7. Final response:
   - For cron jobs that say delivery is local-only and nothing needs user-facing reporting, use `[SILENT]` after successful artifact creation and verification.
   - If a system verification follow-up asks for evidence, report the ad-hoc verifier output explicitly and do not claim "suite green."

## Required recap sections
Unless a local template says otherwise, include:
- **Memo** — one concise narrative summary.
- **Work completed** — concrete activity detected or completed.
- **Decisions made** — explicit decisions; say none were logged if appropriate.
- **Sources and links** — inbox path, changed files, timestamps, links.
- **Blockers** — real blockers only; otherwise "None reported."
- **Follow-ups** — small next checks or interventions.

- If journal generation surfaces stale log errors from long-lived logs, fix the collector contract rather than editing the recap: read the **tail** of each active log (not its first fixed byte range), timestamp-filter lines to the current reporting window, suppress non-git `fatal: not a git repository` output when the journal repo is intentionally a plain artifact tree, and keep current timestamped errors detectable. If a current-day inbox/index is already tainted, preserve a dated repair backup/source manifest, rebuild only the generated current-day collector artifacts, and prove the fresh artifacts exclude stale strings while retaining a current-error fixture. See `references/runtime-collector-freshness-repair.md`.
- If a recap flags a downstream service such as Google Drive MCP, verify the original service after repair (for example Drive API + Hermes MCP `drive_about`) and rerun the snapshot/digest so the next recap is based on fresh state.

## Weekly rollup workflow
Use this in addition to the standard workflow when asked to synthesize the last 7 daily journals into a weekly artifact.

1. Resolve the current date/week with a tool, but base the rollup date range on the **7 most recent daily journal files found**, not only on the calendar week. Daily files can have gaps (weekends, missed snapshots). Note the absence in the rollup header so the date range is honest.
2. Discover the journal root before reading. If the prompt gives `$PRISMATIC_HOME/work/Hermes-Research/journals`, verify that path actually contains recent `YYYY/MM/DD.md` files; if it is sparse/stale and a sibling canonical root contains the current journals, use the root with the newest daily files and note/optionally mirror only if required by the prompt.
3. Read the 7 selected `YYYY/MM/DD.md` files in a single parallel batch. Synthesize across sections; do not dump daily bullets. Preserve concrete paths, issue IDs, PRs, and job names verbatim.
4. Draft the rollup body, then **measure its word count before writing it to disk**. The standard weekly prompt is ≤400 words on the file body. If the first draft exceeds the limit, trim first; do not write a too-long file and assume the verifier will pass. Budget header + sources line + 6 sections (~5 bullets each).
5. Compute the output file from the ISO year/week of the rollup end date unless the prompt says otherwise: `weekly/YYYY-Www.md`. Resolve the ISO week with `date -d <end-date> +"%Y-W%V"`.
6. **Write the real file first** via `write_file` on `weekly/YYYY-Www.md`. **Never write through `latest-weekly.md` with `write_file`** — it is almost always a symlink and `write_file` follows symlinks, overwriting the previous weekly artifact. Use `ln -sfn weekly/YYYY-Www.md latest-weekly.md` (relative target) to repoint the pointer atomically.
7. After the swap, run **`scripts/weekly_rollup_verify.py`** from this skill as the default verification. It checks: file exists and is readable, word count under the limit (default 400; override with `WEEKLY_WORD_LIMIT=...`), all 6 required sections present (matched on plain heading text, no emoji dependence), ≥7 unique daily source citations, `latest-weekly.md` is a relative symlink pointing at the new file, and the previous week's file is byte-identical to a baseline hash if one exists at `/tmp/weekly_rollup_prev.sha256`. Invoke via `python3 <path-to-skill>/scripts/weekly_rollup_verify.py <journals_root> <YYYY-Www>` (e.g. `python3 ~/.hermes/profiles/fred/skills/operations/scheduled-journal-recaps/scripts/weekly_rollup_verify.py /home/ubuntu/work/Hermes-Research/journals 2026-W31`). On the first run of a session, capture the previous-week baseline with `--snapshot-prev`; subsequent runs will detect any unintended drift. Report the script's path, exit code, and the per-check `OK` / `FAILURE` lines verbatim in the final response, and label the output as **ad-hoc verification passed**, never as a canonical suite. Do not reinvent verifier logic with ad-hoc `ls -la / readlink` calls — the reusable script already covers everything and is the audit trail if a verification follow-up arrives later.
8. If a mistaken write through `latest-weekly.md` overwrites an older weekly file, restore that older file before finishing. **First-choice restore source (2026-08-23, verified working): the session DB** — the prior weekly rollup was delivered as the final response of its cron session, so `session_search(query='\"Www\" \"Week in Review\"')` returns the full verbatim artifact; rewrite the file from that content, then re-capture the `--snapshot-prev` baseline (a baseline taken after the clobber is self-certifying — it hashes the already-wrong file). Only fall back to reconstructing from the week's 7 dailies if no prior session artifact exists. Also: capture `--snapshot-prev` **before** any write into the journals tree, not after — the 2026-08-23 session captured it post-write and the prior-week check passed trivially.

## Ad-hoc verification pattern

### First choice: use the canonical verifier, don't reinvent it
The skill ships a reusable `scripts/verify_becca_recap.py` that already implements every check below (header shape, template sections + bullets, inbox cross-reference, snapshot count with read-skew tolerance, full-ISO timestamp fidelity, HD framing, symlink-by-name). **For every Becca next-step daily recap, do this:**

```python
import shutil, subprocess, pathlib

src = pathlib.Path("~/.hermes/profiles/orchestrator/skills/operations/scheduled-journal-recaps/scripts/verify_becca_recap.py").expanduser()
dst = pathlib.Path(f"/tmp/hermes-verify-becca-{YYYY-MM-DD}.py")
shutil.copyfile(src, dst)
r = subprocess.run(["python3", str(dst)], capture_output=True, text=True)
print("exit:", r.returncode); print(r.stdout)
# Do NOT unlink dst in this turn. The verification gate is state-per-turn:
# a post-green delete re-fires the "no fresh evidence" nudge next turn
# (observed 2026-08-13 and reproduced 2026-08-22). Delete only after the
# gate has been quiet for a turn (post-gate cleanup, not this turn).
```

The Hermes verification-nudge system keys on the literal `hermes-verify-` prefix on the temp filename — `cp` (do not `write_file`) the canonical script to `/tmp/hermes-verify-becca-YYYY-MM-DD.py`, run it, delete it. Reinventing the verifier as a fresh heredoc re-implements checks the canonical script already has, defeats the workspace's audit hooks when filename conventions drift, and produces verifiers that miss real defects (e.g. abbreviated timestamps) the canonical script catches. If you typed a bash `mkstemp` heredoc when a Becca recap was the task, patch the recap's session memory with the canonical-script pointer instead.

### When you genuinely need a custom ad-hoc verifier (rare)
When no canonical test command exists AND no `scripts/verify_*.py` in this skill covers the new artifact, create one under `/tmp` using `tempfile.mkstemp(prefix='hermes-verify-', suffix='.py', dir='/tmp')`. Prefer running the verifier directly from `execute_code`/Python (`subprocess.run(['python3', verifier], capture_output=True, text=True)`) instead of nesting shell heredocs inside `execute_code`; nested heredoc quoting can fail in the harness. The verifier must be a fully self-contained Python script: include every import it uses (for example `os` if checking `os.readlink` — and note it is `os.readlink`, NOT `os.path.readlink`; the latter raises `AttributeError: module 'posixpath' has no attribute 'readlink'`, encountered 2026-08-23) so evidence does not fail on a harness mistake. The verifier should check the changed behavior, not just file presence. For journal recaps, verify:
- recap file exists and is readable,
- required sections are present,
- source inbox and meaningful changed paths/timestamps are cited,
- **every full-ISO inbox timestamp is cited verbatim in the recap (abbreviation fails the check)**,
- when a local template was used, the recap cites the template path and the verifier checks that citation,
- quiet-day summaries explicitly state decisions/blockers rather than leaving placeholder bullets,
- weekly rollups stay under the requested word limit and cite the selected 7 daily files/date range,
- `latest.md`, `latest-weekly.md`, or equivalent is a symlink when expected, has the expected portable relative target, and resolves to the new recap,
- the verifier stays on disk through the verification gate (delete only post-gate — a same-turn cleanup re-fires the nudge, observed 2026-08-13 and 2026-08-22).

Label this as **ad-hoc verification**, not a passing canonical suite.

### `execute_code` verifier-writing pitfalls (encountered this session)
When assembling a verifier inside `execute_code` rather than copying the canonical script, the following harness footguns have all surfaced in real sessions:

- **`os.write(fd, str)` raises `TypeError: a bytes-like object is required`.** Pass `pathlib.Path(fd).write_text(script)` or write bytes — `os.write` does not coerce strings.
- **Python f-strings eat bash `{...}` braces.** Inside `f"""..."""`, any literal `{` or `}` you want in the rendered shell script must be escaped as `{{` / `}}`. A common failure: writing `f"if grep -q \"## {sect}\""` silently substitutes the Python variable, not a bash brace. Use plain string concatenation (or `.format()` with named placeholders) when embedding bash in Python.
- **`mkstemp()` returns `(fd, path)` — close `fd` first.** `tempfile.mkstemp` opens the file; calling `pathlib.Path(path).write_text(...)` while the fd is still open can interfere on some filesystems, and the fd leaks across the script. Always `os.close(fd)` immediately after creation (or use `NamedTemporaryFile(delete=False, ...)` if you also want manual cleanup).
- **The outer `execute_code` wrapper script needs its imports too (2026-08-20).** The self-containment rule above applies to the verifier body, but the wrapper that launches it is a separate script: a run that called `subprocess.run([sys.executable, script], ...)` without `import sys` at the top of the execute_code code crashed with `NameError: name 'sys' is not defined` before the verifier ever ran. Include every import in **both** layers — wrapper and verifier — or the evidence run dies in the wrapper and the whole verification turn burns on a re-run.
- **Nested `subprocess.run(['bash', heredoc_string], ...)` quoting breaks at the third nesting layer.** If you need bash inside Python inside `execute_code`, write the bash script to `/tmp/hermes-verify-*.sh` (with `hermes-verify-` prefix still works for sh) and run it via `subprocess.run(['bash', path], capture_output=True, text=True)`. Otherwise pull the body into pure Python and skip bash entirely.
- **`awk '/p1/ && /p2/{action}'` is a syntax error.** `/regex/` in awk is a pattern expression, not a boolean operand, so `&&` between two patterns does not typecheck. The error is `awk: cmd. line:1: /p1/ && /p2/{...} / syntax error`. The correct shapes are: (a) two patterns with no `&&` (awk evaluates each pattern against the current line independently): `awk '/p1/{f=1} /p2/{f=0}'` means "if /p1/ then f=1; if /p2/ then f=0"; (b) state flag with explicit boolean: `awk 'BEGIN{f=0} /p1/{f=1; next} /p2/{f=0} f && /p3/{action}'` — the `f && /p3/` is a real boolean because `f` is a numeric variable (0 or 1) and `/p3/` evaluates to 1 (match) or 0 (no match) in numeric context. Encountered 2026-08-12 in a Becca recap verifier that tried to express "if next snapshot block contains journal file path" with `/p1/ && /p2/`; the verification failed not because the recap was wrong but because the verifier's awk was malformed. The fix is to choose (a) or (b); pure-Python `for line in file: if re.search(p1, line): f=1; ...` also avoids the issue entirely.

If the first ad-hoc verifier fails with one of these, the recap is fine — fix the verifier and re-run. Do not treat harness bugs as recap failures.

## Pitfalls
- Do not stop after writing the markdown; update the latest symlink and verify it.
- Do not over-report a quiet inbox. A concise quiet-day journal is enough.
- Do not invent decisions or blockers from sparse snapshot data.
- Do not surface stale local commitments as current blockers when a linked Linear issue is already Done; query Linear live or mark the local commitment resolved.
- Do not treat `[SILENT]` as permission to skip the local artifact or verification; it only suppresses the final delivery when appropriate.
- **Cite full ISO timestamps, not abbreviated forms.** When the Sources and links section references multiple inbox snapshot timestamps, every entry must be the full `YYYY-MM-DDTHH:MM:SSZ` form (e.g. `2026-08-04T00:00:33Z, 2026-08-04T01:00:34Z, ...`). Do not drop the date prefix on the middle entries (`...T00:00:33Z, 01:00:34Z, 02:00:36Z...`) — that shorthand looks tidy in prose but is unverifiable per-timestamp and the `scripts/verify_becca_recap.py` verifier will flag the recap as missing every full-ISO timestamp. Two ways to write it: a long bullet list of individual bullets, or a single bullet with full ISO form for every entry. The abbreviation habit was inherited from the prior-day recap style; it is a fidelity defect, not a convention to preserve.
- For weekly rollups: count the file's word count against the prompt's limit **before** writing it. Initial drafts commonly run 25-50 words over; trim in place rather than writing a too-long file and patching after.
- For weekly rollups: when the 7 most recent daily journals have gaps (e.g. 07-20 and 07-25 missing), say so explicitly in the header — "7 journals found; 07-20 and 07-25 absent" — rather than silently covering a 9-day span. The date range is the 7 files actually read, not the calendar week.
- For weekly rollups: never use `write_file` on `latest-weekly.md`. It is a symlink and `write_file` will overwrite the previous weekly. Always write the real `weekly/YYYY-Www.md` first, then `ln -sfn weekly/YYYY-Www.md latest-weekly.md`.
- For weekly rollups: never use `cp` to update `latest-weekly.md`. **Two distinct clobber variants have both been observed** — 2026-08-16: `cp` replaced the symlink with a regular file (pointer lost, previous weekly file survived); 2026-08-23: `cp weekly/2026-W34.md latest-weekly.md` (symlink → `weekly/2026-W33.md`) **wrote THROUGH the symlink and destroyed the previous weekly file** (W33's content became W34's; the symlink itself stayed intact with unchanged mtime, so `os.path.islink` returns `True` and a casual `ls -la` looks fine). The only correct operation is `ln -sfn weekly/YYYY-Www.md latest-weekly.md`. After any update verify BOTH `os.path.islink('.../latest-weekly.md') == True` AND that the target file's content matches the new rollup's label (e.g. `grep -c "2026-W34"` > 0 in the target) — a write-through clobber passes the islink check. If `False`, repair with `rm && ln -sfn`; if the target content is wrong, restore it from session history (see the 2026-08-23 drift entry).
- If a verification nudge arrives after a silent cron result, run a fresh focused verifier even if one already passed earlier in the turn; the workspace verifier may only accept evidence produced after the nudge. Summarize the temporary `/tmp/hermes-verify-*.py` path, cleanup status, checked behaviors, and label it explicitly as **ad-hoc verification**, not "suite green." This system follow-up overrides local-only silence for that turn: report the verifier evidence instead of returning `[SILENT]`.
- **If the verification nudge re-fires in subsequent turns, run the canonical verifier again — do not stop.** The audit hook is state-per-turn: a fresh prompt sees no persistent disk evidence from earlier in the same session even if you ran a verifier minutes ago. The right response to "edited code, unverified, no canonical test detected" is **always** to copy `scripts/verify_becca_recap.py` to `/tmp/hermes-verify-becca-YYYY-MM-DD.py` and run it (leave the temp script on disk through the gate — deleting it re-fires the nudge next turn; delete only post-gate), and report the new exit code. Do not argue that prior evidence exists; do not return `[SILENT]`; do not write a brand-new heredoc verifier when the canonical one is one `cp` away. Repeated-prompt re-runs of the same canonical verifier with exit 0 / PASS are the right answer until the nudge stops firing.
- **Personal morning-briefing cron ≠ recap file cron.** This skill is for jobs that write a recap to disk. The *deliverable* Telegram cron that reads the recap and tells Becca "Good morning, here's what moved overnight" is a different job with a different shape (one signal line, not a recap file). See `personal-named-recipient-telegram-briefings` for the delivery-side contract and its reconciliation with the strict `telegram-cron-output-contract`.
